# Account and build-order API exports — items 78A and 78B

These source slices add an explicit server transport on the existing authenticated `GET /v1/me/export`: `?format=ndjson`, optionally `&details=1`, and authenticated `GET /v1/export/build-orders.csv` / `.ndjson`. Absent account format and `format=json` preserve the existing materialized JSON response and attachment name. Item 78 remains partial; Settings cards, browser export ownership/progress/cancel, replay packs, filename templates, browser ZIPs, disclosure/help and managed replay-storage GET CORS remain later work.

The NDJSON format is `sc2tools-account-export`, version 1, distinct from the restorable `sc2tools-backup` snapshot. It starts with a metadata record containing the captured authenticated owner, timestamp and details selection, declares each present collection (including empty ones), emits one record per row and one user record, and finishes with `type: "complete"` plus per-collection row counts. EOF without that terminal record means incomplete. This is a sequential read, not a database point-in-time snapshot.

Legacy JSON and NDJSON use the same collection/projection source. It retains all nine existing user-scoped collections, identity submissions, sounds metadata, coaching assignments/Locker relationships/calendars, user projection, player channels, five reviews collections and admin audit redaction. The exported `USER_SCOPED_COLLECTIONS` compatibility surface remains available from `gdpr.js` for snapshot consumers. Existing shared-party redactions remain in one extracted policy module. Full account exports can contain the owner's live overlay tokens and device token hashes; they are private account downloads and must never be described or handled as redacted support bundles.

Each NDJSON export cursor receives the request AbortSignal and `batchSize: 1`, and closes in `finally`, including consumer return and failed output. The route captures the owner once and never retargets asynchronous work from a later mutable request auth object. It waits for response drain before asking the generator for another row, cancels on request abort/response close and awaits outstanding work/cleanup. Started-stream failures close without a success trailer or serialized private exception; pre-stream failures return only `export_unavailable`. Downloads use private/no-store headers and fixed generated attachment names.

One process-shared HTTP export slot in `routes/exportAdmission.js` covers account JSON/NDJSON and build-order CSV/NDJSON, across owners and handler instances. After authentication/options/cursor validation, overload returns only HTTP 503 `export_busy` with private/no-store before quota or any export read is invoked. There is no waiting queue. The slot remains reserved until both actual quota/read/generator/cursor/detail cleanup settles and the response emits finish, close or error. Closing a client alone cannot admit replacement work while cleanup is held; duplicate old-response events cannot release a newer lease. A late JSON result after client closure is discarded. This bounds concurrent HTTP export work in one API process; the legacy JSON format still materializes an account-sized response for compatibility and is not a per-record memory-bound transport.

The explicit encoded-record limit is 17 MiB including newline. A valid 16 MiB BSON document can exceed this limit after JSON escaping or binary encoding; such a row terminates the incomplete export before any part of that row is written. One Mongo document, one encoded record and the existing one-document shared Locker are retained, rather than an account-sized array. The legacy JSON format continues to materialize its response for compatibility.

Optional game details use `GameDetailsService.findMany` with the five `HEAVY_FIELDS`, strict reads and singleton batches/concurrency 1. This avoids storage pointer metadata, unbounded retained result Maps and sibling read settlement gaps. The global R2 two-active/32-waiter gate and existing 6 MiB R2 object JSON budget are unchanged. Each owned game's details record explicitly reports `available` or `missing`; a provider/read failure prevents completion. MongoDetailsStore now forwards its supplied signal and finally closes its own detail cursor as well.

Build-order exports reuse the effective owner-view replay-library filter: live/deletion/exclusion gates, global filters, result aliases, matchup and search. A metadata cursor projects only `_id`, `date`, `gameId`, uses the supplied signal, `batchSize: 1`, a 30-second Mongo query budget and a literal 2,001-row limit, validates/copies each bounded row, and closes before response headers. Only the first 2,000 games receive detail reads; the sentinel determines continuation. Keyset pagination preserves historical Date/string/number/null cohorts and ObjectId ties. It is sequential pagination, not a point-in-time archive; concurrent edits/deletions or backdated inserts can change membership.

The dedicated versioned HMAC cursor uses the existing server pepper with domain separation. Production `loadConfig` supplies a validated 32-byte Buffer; the service defensively copies it into a private immutable crypto KeyObject, so later mutation of the config buffer cannot retarget existing signing. Invalid key types/lengths fail closed. It contains owner HMAC, effective base-match hash, format, typed position and initial issuance/fixed 24-hour expiry, with no raw search or token. The canonical hash explicitly represents Date/ObjectId/RegExp and sorts only known unordered Mongo set/logical arrays. Alias/case/whitespace/bound/set normalization applies before hashing; changed effective scope/owner/format rejects rather than retargets. Every continuation authenticates normally and costs another quota admission. Invalid/tampered/foreign cursors fail before quota; expired cursors return fixed HTTP 410. No per-row auth leases or additional secret/flag are introduced.

Build-order quota is one atomic existing-user `findOneAndUpdate`, `upsert: false`, fenced by absent `_gdprMutation`. The new operational `users.buildOrderExportQuota` field stores version 1 and at most three Mongo-server Date timestamps, retaining only admissions within the rolling hour. Missing field initializes; malformed/null/unsupported/future/oversized state fails closed and is not repaired. Missing/blocked/corrupt/full quota returns the same HTTP 429 `export_rate_limited` with conservative `Retry-After: 3600`, concealing the distinction. The field stays outside restored preference/profile allowlists. Each valid admitted page consumes one slot; read failure, abort or unknown write acknowledgement causes no retry/refund. An admitted quota write is awaited to actual settlement after disconnect; it cannot release admission early or lead to metadata reads after cancellation.

Four owned singleton `GameDetailsService.findMany` calls run per bounded batch, with only `buildLog`/`oppBuildLog`, `strict: true`, `concurrency: 1` and a shared child signal. First read or validation failure immediately aborts siblings; `allSettled` joins every admitted reader before returning/releasing. No next batch is admitted while output is under backpressure. Existing R2 two-active/32-waiter and 6 MiB JSON object limits are unchanged. At most four returned detail Maps plus 2,001 small metadata values are retained; Mongo still has a bounded single-document transient. Missing/deleted/unreadable/corrupt required logs are failure, while genuinely present empty arrays yield zero events.

Event rows have exactly `gameId, side, time, supply, name`, with side `me` or `opponent`. Stored order and duplicate events are preserved. Legacy logs are bounded to 5,000 lines per side and 256 characters per line. Exact `[minutes:ss] name` parsing requires seconds 00–59, nonempty names, valid text and nonnegative safe-integer seconds; malformed/overflow/oversized data terminates the page without truncation. Current strings contain no exact supply: NDJSON emits null and CSV emits an empty cell. No per-game compute/catalog/enrichment or approximate supply is invoked. The generated row byte budget is 4 KiB. CSV reuses formula-safe escaping and has only its five-column header/events, with no summary rows. A normal completed HTTP body is required for CSV success; NDJSON uses `sc2tools-build-order-export` version 1 metadata and a final complete record/counts/continuation. Partial EOF or late error is failure. `X-Export-Has-More` and `X-Export-Continuation-Token` are exposed through existing API CORS along with every prior exposed header; consumers must advance only after full successful body completion. This does not change managed replay R2 CORS. Both new search paths are registered in search privacy matching/hints and metadata reads use the existing search-safe Mongo comment.
