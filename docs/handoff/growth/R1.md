# R1: game-start scouting lists each player's last five games

**Shipped.** API, desktop agent 0.25.0 (set on `main`, not published) and help. The Companion's floating Scouting report lists the builds from each player's last five games, newest first, each with your result, the map and the age; a row opens that game's build order. "You" is your games in this matchup. "Opponent" is your games against this player in every matchup, linked accounts included. The loading-screen strip shows both lists in short form. A first meeting says so, and a setting that starts on keeps a pinned report closed then.

- **Where the report's two build orders come from (traced).** The agent's `live/*` bridge posts the live envelope; `OverlayLiveService.buildFromOpponentName` adds `streamerHistory`; `LiveGameBroker.latest` holds it; the Companion polls `GET /v1/me/live/snapshot`; `companion_page._live_context` feeds `CompanionPanel("scouting")`, and a chosen game's steps come from `GET /v1/games/<id>/build-order`. The strip reads the device brief (`agentScouting.buildScoutingBrief`, `scouting:brief`).
- **Decisions (ADR 0077).** Both lists ride in a new `streamerHistory.recentBuilds`; an older agent ignores it and the new agent draws today's report when it is missing. The broker removes the lists from both overlay emits, so OBS receives nothing new; the spoken report is unchanged. The brief carries result and build only, and drops the lists first at its byte cap. The opponent's list is not limited to this matchup (the block does not limit it); a row says "as Terran" when the race differs. A display name alone never matches a game, and a failed read leaves the lists out instead of reading as a first meeting. Stacked at the smallest size, the opponent's list comes first.
- **Setting.** `scoutingSkipFirstMeeting`, on by default, gates only the pinned report's own opening, in team games too. It is the one Companion preference that starts on, so the "nothing appears by default" test now names it.
