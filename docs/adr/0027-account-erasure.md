# Account erasure and identity finalization

Account erasure must finish the sign-in account as well as local data. Account DELETE requires a Clerk browser session; a paired device token cannot end the sign-in identity. The API and a verified Clerk `user.deleted` webhook call the same ownership-aware `deleteAll`. No production erasure was executed to implement or test this change.

`GDPR_CLASSIFICATION` explicitly classifies every registered collection. A coverage test fails when a future collection lacks a disposition. Global public catalogs and aggregates are preserved, including the independently shipped `site_config` collection. The classification is an audit inventory; dedicated services perform actual deletion and shared-record anonymization.

Before token owners disappear, erasure iterates their active and revoked overlay links in batches and purges token-keyed Studio, viewer, prediction, clip and engagement records, including canonical `studioKey` and legacy `token` Studio rows. Cached token resolutions are invalidated and active user/overlay sockets disconnected. Sound bytes are deleted; the GDPR export contains sound metadata only. Private object stores and snapshots must purge successfully before the user row and provider identity are removed.

Public pairing token issuance, finite token-authenticated HTTP controls, authenticated owner writes and recipient notification writes use renewable shared leases on the users row. Erasure waits for admitted writes, obtains the existing exclusive GDPR fence, and never removes a fence to make progress. Interrupted HTTP writes retain their expiring lease because their handler could still be running. The identity guard prevents a late valid JWT or identity upsert from recreating the deleted account.

After private purges, a keyed `pending_identity_deletions` intent is persisted before removing the users row. Provider deletion runs only after that row is absent. A failure returns successful local deletion with `identityDeletionPending: true`; a process timer retries through the existing renewable `jobLocks` pattern, with backoff and a bounded batch. Pending records do not expire. The retry can resume a crashed local purge only after its previous lease has expired; it never clears an existing lock. Verified deleted webhooks acknowledge provider absence without calling the provider again. Completed records drop plain Clerk/internal IDs and retain a domain-separated HMAC guard for 30 days. This minimal guard expires automatically. No email channel, external scheduler or new infrastructure is introduced.

The three-step dialog offers export, displays live removed/anonymized counts, then requires exact `DELETE`. A successful purge followed by a sign-out error retries only sign-out. The goodbye page and privacy policy read a sanitized subset of the existing cached Atlas schedule; an unreadable schedule is unknown, never an invented duration. Counts are a live estimate, not an erasure reservation. Review comments on other users' requests survive with a deleted-author marker. Already-created service backups expire under their configured schedule rather than being edited individually.

Native unauthorized-token handling is supplied by agent pairing recovery (#661, preserved in runtime/installer drafts #668/#672): repeated confirmed 401 responses show “This PC was unlinked” and stop automatic sync. The account-erasure change does not fork those native call sites.

Operations: inspect `pending_identity_deletions` state/attempts/nextAttemptAt and sanitized retry codes when a provider outage delays finalization. Never delete pending rows or user fences to unblock a retry. Fix provider access or the failed data-store purge and let the durable job retry. Completed rows intentionally have no identity IDs. Existing snapshot restore rollback constraints in ADR 0026 remain in force.

Rollback: prefer a compatible forward fix. Keep identity guards and the retry worker deployed while pending records or completed 30-day guards exist; the previous auth path can recreate deleted identities from old JWTs or late upserts. Temporarily disable new account-deletion entry points if necessary instead of dropping retry records, removing locks, or restoring erased user data. There is no down-migration that resurrects an erased account.
